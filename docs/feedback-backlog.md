# 사용자 피드백 백로그

첫 링크 테스트(2026-08, 지인 대상)에서 받은 코멘트와 그 처리 계획.
**아직 아무것도 적용하지 않았다.** 다음 수정 라운드에서 합의된 것부터 넣는다.

---

## 받은 코멘트 원문

1. 중간중간 선택지가 있는 거 좋음 (지루하지 않음)
2. 책에 대해 배경지식이 없는 사람은 내용이 잘 이해가 안 됨
3. 번역에 어색한 부문이 많음 (비문 다수)
4. 다 읽고 나면 그냥 작품만 다시 읽어보는 형태로 (다시읽기 / 선택지 없이 읽기) 형태 추가 필요
5. 어투가 좀 끊어지는 느낌. 내가 수정할 수 있도록 만드는 것과, 기본적인 어투를 레퍼런스로 먹이면 그 톤엔 매너로 제작할 수 있을지

## F1 — 배경지식 없으면 이해가 안 된다

**규모: 중 ~ 대. 이번 피드백에서 가장 중요하다.**

설명을 덧붙이면 되는 문제가 아닐 수 있다. 각색이 원작을 이미 아는 사람 기준으로
압축돼 있다는 신호로 읽는 편이 맞다. 『이방인』 2부(재판)는 1부에서 무슨 일이
있었는지를 독자가 붙들고 있어야 작동하고, 『변신』은 가족의 돈 사정이 4페이지에
한 번 스치고 지나간다.

세 가지 방법이 있고 비용과 효과가 다르다.

| | 무엇 | 코드 | 글 | 위험 |
|---|---|---|---|---|
| **(a)** 표지에 「들어가기 전에」 3~4줄 | 작가·발표연도·상황 한 문단 | 1시간 (json `intro` 필드 + 표지 렌더) | 작품당 30분 | 낮음 |
| **(b)** 페이지별 접히는 각주 | 인물·용어 한 줄 | 반일 (payload에 note 배열, 접힘 UI) | 작품당 1시간 | 읽기 흐름이 끊긴다 |
| **(c)** 각색문 국소 재작업 | 막히는 대목을 다시 쓴다 | 0 | 작품당 반일~하루 | 없음 (근본 해결) |

**추천: (a)를 먼저 넣고, `/admin`의 페이지별 이탈률로 어디서 막히는지 확인한 뒤
(c)를 그 페이지에만 적용한다.** (b)는 각주를 여는 순간 "공부하는 화면"이 되므로
spec §2(읽는 동안 아무것도 가르치지 않는다)와 부딪힌다. 보류.

(a)를 넣을 자리는 표지(`app/w/[slug]/page.tsx`)다. 1페이지 앞에 0페이지를 두는 안도
있으나, 그러면 진행 표시(`progress`)의 칸 수와 페이지 번호가 전부 밀린다.
표지가 싸고 되돌리기도 쉽다.

## F2 — "번역에 어색한 부문이 많음 (비문 다수)"

**규모: 중. 코드 변경 0, 원고 교정.**

먼저 사실관계 하나. 이 앱에는 번역문이 없다. 출판 번역본은 한 줄도 쓰지 않았고
전부 원문 기반 자체 각색이다(저작권 요건). 그런데도 테스터가 "번역"이라고 부른 것은
**문장이 번역투로 읽힌다**는 뜻이므로, 그 자체가 정확한 지적이다.

원인 후보:
- 원문 구조를 그대로 따라간 문장 (특히 『이방인』 1인칭 과거 나열)
- 주어를 생략해도 되는 자리에서 "나는"을 반복
- "~것이었다", "~하는 것이다" 남발
- 한 문장에 절이 셋 이상 들어간 대목

**손댈 곳:** `content/*/ko.md` 세 편의 본문. 문항과 json은 건드리지 않는다.
**규모:** 작품당 2~3시간.

**문제는 어느 문장이 걸렸는지 모른다는 것.** 두 가지로 좁힌다.

- 자동 검사를 `content:check`에 warn으로 추가 (반일): 한 문장 60자 초과, 한 문단
  안의 "것" 3회 초과, 이중피동(되어지다·불려지다), 같은 종결어미 4연속.
  기계가 잡을 수 있는 것만 잡는다. 나머지는 사람이 읽어야 한다.
- 다음 테스트 배포에서 **문장 신고**를 받는다 — 길게 누르면 "이 문장 어색해요"가
  뜨고 페이지 번호와 문장 인덱스만 남긴다. 규모 반일. 다만 읽기 화면에 버튼이
  하나 늘어나므로 넣을지는 결정 필요.

## F3 — 다시읽기 / 선택지 없이 읽기

**규모: 소. 반일. 다음 수정 1순위로 제안한다.**

가장 명확하고 가장 싸다. `readingPayload()`가 이미 전 페이지 본문을 주고,
세션 없이도 만들 수 있다. 필요한 것은 라우트 하나다.

- `app/reread/[slug]/page.tsx` — 세션 불필요, 문항 렌더 안 함, 열 페이지를 한 스크롤로.
  삽화는 그대로, 진행 표시는 없음.
- 진입점 둘: 결과 화면 하단("선택지 없이 다시 읽기"), 표지(**이미 완독한 작품일 때만**).
- 서비스 워커 프리캐시 목록(`components/PrefetchPages.tsx`, `public/sw.js`)에 이 경로 추가.

**결정 필요:** 완독 전에도 열어줄 것인가. 열어두면 문항을 통째로 건너뛰고
결과만 보러 갈 수 있어 데이터가 오염된다. **완독 후에만 노출**을 권한다.
URL을 직접 치면 열리는 것까지 막을 필요는 없다.

## F4 — 어투가 끊어진다 / 톤 레퍼런스

코멘트가 두 가지를 한꺼번에 말하고 있어 나눠 본다.

### (b) 기본 어투를 레퍼런스로 먹이기 — **규모: 소. 반일. 권장.**

지금 톤 지침은 `docs/spec.md`와 각 작품 md의 「각색 원칙」에 흩어져 있고,
"짧은 문장, 현대 구어 리듬, 감정 형용사 절제" 정도로만 적혀 있다. 이 정도로는
작품이 늘어날수록 톤이 흔들린다.

`docs/style.md`를 만든다. 들어갈 것:
- 문장 길이 분포(중앙 25~35자, 60자 넘는 문장은 페이지당 하나까지)
- 종결어미 배분과 4연속 금지
- 금지 어휘: 철학·문학 용어, 감정 형용사, 번역투 관용구 목록
- 대화 처리 방식(따옴표를 쓰지 않고 문장에 녹인다 — 세 작품이 이미 그렇게 돼 있다)
- 좋은 문장 / 고쳐야 할 문장 대조표 (기존 세 작품에서 실물로 뽑는다)

이게 있으면 다음 작품에서 내가 지킬 근거가 되고, F2의 자동 검사도 이 문서를
기준으로 짤 수 있다. **F2·F4가 사실상 한 작업이므로 묶어서 한다.**

### (a) 내가 직접 수정할 수 있게 — **뜻을 확인해야 한다.**

두 가지로 읽힌다.

1. **원고를 직접 고치고 싶다** → 이미 가능하다. GitHub 웹에서 `content/*/ko.md`의
   본문을 고치면 된다. 단 `> **Q…**` 인용 블록(문항)은 건드리면 안 된다 —
   빌드가 md와 json을 대조해서 어긋나면 실패시킨다. 본문 문단만 고치는 건 안전하다.
   비용 0. `docs/`에 한 페이지짜리 사용법을 붙이면 끝난다.
2. **앱 안에 편집 화면을 만들고 싶다** → 규모가 완전히 다르다. 인증, 저장,
   md↔json 정합성 재검사, 재빌드 파이프라인이 전부 필요하다. **며칠.**
   지금 단계에서는 권하지 않는다. 원고는 세 편이고 고치는 사람은 한 명이다.

---

## F5 — 중간중간 선택지가 좋다

유지. 문항 수를 늘리고 싶은 유혹을 경계한다. 현재 8~12개이고, 이보다 늘리면
"읽는 중 묻는다"가 "설문 푼다"로 바뀐다. 지루하지 않다는 반응은 문항 수가 아니라
문항이 장면 안의 행동으로 위장돼 있어서 나온 것에 가깝다.

## 제안 순서

| 라운드 | 항목 | 예상 |
|---|---|---|
| **1차** | F3 다시읽기 · F1(a) 들어가기 전에 · F4(b) `docs/style.md` | 하루 |
| **2차** | F2 세 편 교정 패스 + 자동 검사 warn | 이틀 |
| **3차** | F1(c) 각색문 국소 재작업 — `/admin` 이탈 페이지 확인 후 | 작품당 반일 |

시지프 삽화 교체는 이와 별개로 언제든 들어갈 수 있다.

## 결정이 필요한 것

1. F4(a)가 「GitHub에서 md 직접 편집」인가, 「앱 안 편집 화면」인가
2. 다시읽기를 완독 전에도 열어줄 것인가 (권장: 완독 후에만)
3. 배경 설명을 표지에 둘 것인가, 1페이지 앞 0페이지로 둘 것인가 (권장: 표지)
4. 문장 신고 버튼을 읽기 화면에 넣을 것인가 (읽기 화면에 버튼이 하나 는다)
