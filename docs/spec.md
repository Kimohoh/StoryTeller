# spec.md — 고전문학 능동적 읽기 앱 (작업명 미정)

첫 작품: 카프카 『변신』(1915, 퍼블릭 도메인)
이 문서 하나로 클로드 코드 작업을 시작할 수 있게 쓴다.

---

## 1. 제품 한 줄

퍼블릭 도메인 고전을 8~12페이지로 각색해 읽히고, 의견이 갈리는 지점마다 선택지를 넣어 독자의 좌표를 누적한다. 다 읽으면 유형 진단이 나오고, 같은 유형·다른 유형 사람들의 코멘트를 읽고 쓸 수 있다.

## 2. 반드시 지킬 것

- **선택은 이야기를 분기시키지 않는다.** 텍스트는 고정, 선택은 기록만. 분기시키면 제작비가 2^n이 되고 원작이 팬픽이 된다.
- **축은 읽는 중에 절대 노출하지 않는다.** 진행 바에 "가치관 측정 3/8" 같은 표시가 뜨는 순간 사람들이 답을 연기하기 시작한다. 축은 결과 화면에서 처음 등장한다.
- **문항은 전부 장면 내부의 구체적 행동으로 위장한다.** 추상 질문 금지.
- **유형 이름에 가치 서열이 없어야 한다.** 한쪽이 더 성숙하거나 따뜻해 보이면 다음 작품부터 사람들이 그쪽으로 답한다.
- **저작권.** 원문 퍼블릭 도메인 + 자체 각색만 사용. 국내 출판 번역본 문장은 한 줄도 쓰지 않는다. 생존 작가 작품(예: 『칠드런 액트』)은 각색 대상에서 제외.

## 3. 축 설계

앱 공통 축 2개. 작품이 늘어나도 이 둘은 공유하며, 읽을수록 사용자 좌표가 정밀해진다.

| 축 | 내부 정의 | 양(+) | 음(−) | 우회하는 것 |
|---|---|---|---|---|
| A | 책임의 소재 | 개인 | 바깥 | 좌/우 성향 |
| B | 의미 부여 | 서사 | 사실 | 종교성·초월 지향 |

세 번째 축(결과 vs 방법)은 A·B와 상관이 높아 MVP에서 제외. 필요하면 작품별 로컬 축으로 붙인다.

유형 이름은 **작품마다 다르게**, 작품 속 사물에서 딴다. 『변신』 기준:

| | B+ 서사 | B− 사실 |
|---|---|---|
| **A+ 개인** | 바이올린 | 시간표 |
| **A− 바깥** | 액자 | 창문 |

## 4. 콘텐츠 구성

- `content/metamorphosis.ko.md` — 각색 원문(사람이 읽고 고치는 정본)
- `content/metamorphosis.ko.json` — 앱이 먹는 구조(페이지, 문항, 축, 가중치, 삽화 키)

8페이지 + 질문 없는 9페이지(결말). 문항 8개, 축 배치는 **B-A-B-A-B-A-B-A** 교차. 한 축 문항이 몰리면 사람들이 앞 답에 맞춰 일관성을 만들려 들어 좌표가 뭉개진다.

결과 화면 마지막에 `Ungeziefer` 반전 문구가 들어간다 (md 파일 끝 참조). 제목의 "바퀴벌레"를 회수하는 장치이므로 빼지 말 것.

## 5. 삽화 교체 구조 ★

임시 SVG를 나중에 외부 생성 이미지로 갈아끼울 때 **콘텐츠 파일을 건드리지 않는 것**이 요구사항이다.

```
content/metamorphosis.ko.json      illustration_key: "p3_door_opens"   ← 키만 있음
assets/illustrations/manifest.json  키 → 실제 에셋 매핑
assets/illustrations/metamorphosis/
    p3_door_opens.svg
    p3_door_opens@2x.png            (교체본이 생기면 여기 추가)
```

`manifest.json` 형태:

```json
{
  "p3_door_opens": {
    "type": "svg",
    "src": "metamorphosis/p3_door_opens.svg",
    "alt": "열린 문에서 쏟아진 빛 웅덩이 안에 낮고 긴 형체가 드러나 있다",
    "credit": null,
    "version": 1
  }
}
```

규칙:

- 콘텐츠 JSON은 **키만** 참조한다. 파일 경로·확장자·치수를 알지 못한다.
- 렌더러는 `type`을 보고 인라인 SVG로 넣을지 `<img>`로 넣을지 결정한다. 호출부는 `<Illustration k="p3_door_opens" />` 하나로 통일.
- 교체 = manifest 한 줄 수정 + 파일 추가. 콘텐츠·스키마·코드 변경 없음.
- `alt`는 manifest에 둔다. 이미지가 바뀌면 설명도 같이 바뀌어야 하니까.
- `version`을 올리면 캐시 무효화. 앱 업데이트 없이 삽화만 교체 가능.

현재 8장 SVG는 **와꾸 확정용 임시본**이다. 외부 제작 프롬프트는 `docs/image-prompts.md`.

## 6. 채점

**계산은 클라이언트, 진실은 서버.** 서버가 저장하는 건 좌표가 아니라 원본 선택이다.

좌표만 저장하면 축 가중치를 영원히 못 바꾼다. 100명 쌓인 뒤에 "Q4가 A축을 제대로 못 잰다"를 알게 될 가능성이 높은데, 그때 원본 선택이 남아 있어야 전원 소급 재계산이 된다.

채점표는 서버에서 내려받는다. 작품 데이터에 `scoring_version`과 문항별 `axis`/`weight`를 실어 보내면 클라가 즉시 계산하고(왕복 없음), 규칙 변경은 앱 업데이트 없이 된다.

좌표: 축별로 `Σ(value × weight) / Σ(weight)` → −1.0 ~ +1.0 정규화.

## 7. 스키마 (SQLite)

```
works        id, slug, title, scoring_version, axes(json)
questions    id, work_id, page_no, order, axis, weight
choices      id, question_id, label, value            -- value: -1 | +1
sessions     id, work_id, user_id, scoring_version, started_at, completed_at
answers      session_id, question_id, choice_id, answered_at
             PK(session_id, question_id)
comments     id, session_id, question_id NULL, body, axis_x, axis_y, created_at
```

- `answers`에 좌표 없음 — 좌표는 `answers` + `scoring_version`으로 유도되는 파생값
- `comments`에는 좌표를 스냅샷으로 박는다 — 나중에 그 사람 좌표가 바뀌어도 그때 그 관점으로 쓴 글이라는 맥락이 유지돼야 한다
- `answered_at` 필수 — 어느 문항에서 오래 망설이는지가 문항 품질 지표다. 3초 만에 넘어가는 문항은 축을 못 재고 있는 것
- `questions.axis`가 테이블에 있는 게 핵심. 튜닝이 코드 수정이 아니라 데이터 수정이 된다

## 8. 결과 화면

- 4분면으로 딱 자르지 말고 **좌표 + 근접 유형**으로 준다. 경계선 근처 사람에게 안 맞는 진단문을 주면 신뢰가 무너지지만, "당신은 창문에 가깝지만 액자와 한 뼘 거리입니다"는 오히려 정확하게 느껴진다.
- 진단문은 세 단락: ① 당신이 읽은 방식 ② 그 시선이 현대에서 작동하는 지점 ③ 이 시선의 사각지대. ③이 있어야 칭찬으로 안 읽히고, 다른 유형 코멘트를 보러 갈 이유가 생긴다.
- **실제 선택 한 줄을 진단문에 인용해 박는다.** "3페이지에서 당신은 계속 말을 거는 쪽을 택했습니다" — 이 한 줄이 일반론 열 줄보다 본인 얘기처럼 읽힌다.

## 9. Cold start

통계가 0인 초기에 분포를 보여줄 수 없다. **가짜 데이터로 채우지 않는다.** 들키면 끝이다.

대신 각 선택지마다 "그렇게 고른 사람의 논거"를 콘텐츠로 미리 써둔다. 실제 유저 코멘트가 쌓이면 그 아래로 밀려나고, 초기엔 그게 대화 상대 역할을 한다. 첫 유저도 혼자가 아니게 되는 게 핵심.
